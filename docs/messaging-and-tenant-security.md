# Messaging and tenant-security rollout notes

## Customer WhatsApp/SMS

`CustomerMessagingPreferences` is the authoritative consent record. Unknown or missing consent is not permission to message. Record the channel, normalized destination, source of consent, and timestamp. An opt-out must update the record before any queued send is attempted; suppress queued messages after opt-out. Treat provider delivery callbacks as untrusted input: verify the provider signature, reject stale/replayed callbacks where the provider supplies event IDs, and never log message bodies or credentials.

`src/messaging/provider.js` defines the provider-neutral send contract. Vendor adapters must be injected from server configuration, use idempotency keys, classify retryable failures, and redact provider responses. Do not claim a message was delivered merely because the provider accepted it. Customer reminders must only be scheduled after the consent gate is checked and checked again immediately before dispatch.

## Row-level security rollout gate

> **Status (2026-10-23):** this section is the original rollout rule. Migrations `0032` and `0033` now enable and force row-level security on every legacy tenant table, the access paths and workers were converted, and restricted-role tests pass in CI (audit rev 10). Staging runs as a restricted role. Current rules and gaps are in `SECURITY.md`; the text below still describes what must stay true.

RLS must not be enabled on existing tenant tables until every database access path sets a transaction-local tenant context on the same checked-out PostgreSQL connection, including HTTP requests, workers, CLI jobs, and tests. `SET LOCAL app.business_id = ...` must be parameterized via `set_config` inside a transaction; connection-pool session state must never leak between tenants. Platform jobs need a separate narrowly privileged role/path. Table owners and roles with `BYPASSRLS` can bypass ordinary policies; use `FORCE ROW LEVEL SECURITY` only after owner/job behavior has been verified.

Migration `0030_supplier_purchase_order_rls.sql` enables and forces RLS only for the new `Suppliers`, `PurchaseOrders`, and `PurchaseOrderItems` tables. Their HTTP route queries run on a checked-out client inside a transaction and set `app.business_id` with parameterized `set_config(..., true)`; missing context fails closed. Migration `0031_purchase_order_expense_category.sql` links an optional expense category so received shipments can create their expense in the same transaction as the stock receipt.

**Legacy tenant tables:** at the time of `0030` these had no policies. That changed in `0032` (see the status note above). The rule for any future table or access path stays the same: transaction-local context on the same checked-out connection, cross-tenant SELECT/INSERT/UPDATE/DELETE tests, missing-context denial, pool reuse across two tenants, background jobs, and migration/adoption checks, run as a restricted role. Do not rely on application filters as a substitute for these tests.

### Provider configuration

Optional adapters are configured with `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, and `TWILIO_SMS_FROM` for SMS, or `META_WHATSAPP_ACCESS_TOKEN`, `META_WHATSAPP_PHONE_NUMBER_ID`, and optionally `META_GRAPH_API_VERSION` for WhatsApp (sending); inbound WhatsApp also needs `META_WHATSAPP_APP_SECRET` and `META_WHATSAPP_VERIFY_TOKEN`, and `META_WHATSAPP_TEMPLATE_LANGUAGE` names the language the message templates were approved in (default `en`). See `WHATSAPP_SETUP.md`. Keep credentials in the deployment secret manager. The provider factory does not make a send unless that channel is configured. `sendCustomerMessage` checks current consent before invoking the provider; workers must call this helper rather than calling `provider.send` directly for customer destinations.

**Customer opt-out (step-08b).** Sending needs the business's `OptedIn` record in `CustomerMessagingPreferences` **and** no standing stop in `MessagingSuppressions`. Two ways out for the customer: (1) the unsubscribe link in every message, `/unsubscribe#<token>`, an HMAC-signed token carrying the business and preference IDs (key from `CSRF_SIGNING_KEY`, else `JWT_SIGNING_KEY`; the token never expires and sits in the URL fragment so it stays out of logs). Preview changes nothing; confirm sets that preference to `OptedOut` with source `customer_link`. Forged, malformed, unknown and other-business tokens all give the same 404, and a forged token makes no database call. (2) A STOP reply to the shared Twilio sender: `POST /api/messaging/twilio/inbound` checks `X-Twilio-Signature` (URL from `TWILIO_INBOUND_WEBHOOK_URL`, else `PUBLIC_BASE_URL` plus the path) and records a sender-wide stop, because one sender number serves every shop. START lifts that stop only; it never restores a business's consent. A Twilio 21610 refusal at send time is recorded the same way and is not retried. `MessagingSuppressions` has no `BusinessId` and no row-level security (like `EmailSuppressions`); it is written only by the webhook and the worker. Staff cannot record `OptedIn` over a customer's own opt-out (409 `customer_opted_out`) and cannot use the source `customer_link`. WhatsApp has no inbound STOP yet (decision 17).

The existing appointment reminder worker remains the staff-notification flow. Customer reminders use the separate durable outbox and worker described below.

## Order and payment messages (step-16b)

`CustomerEventOutbox` (migration `0040`, forced row-level security) holds queued messages about an order or a payment. They are separate from the appointment reminders on purpose: that table, its triggers and its unique key are specific to appointments. Rows hold references only; the text is built at send time. A row is queued in the transaction of the event that causes it, only for a customer with a current `OptedIn` record and no standing stop, and consent and the order or payment are read again just before sending. See `NOTIFICATION_SYSTEM.md`.

## Durable customer appointment reminders

Migration `0029_customer_message_outbox.sql` creates `CustomerMessageOutbox` and database triggers that enqueue reminders at 24 hours and 2 hours before scheduled appointments for currently opted-in destinations. The same transaction cancels queued reminders when appointments are cancelled/rescheduled or consent is withdrawn. The `CUSTOMER_MESSAGE_WORKER_ENABLED` and `CUSTOMER_MESSAGE_WORKER_POLL_SECONDS` settings control the dispatcher. It leases rows with `SKIP LOCKED`, checks appointment state and consent again immediately before sending, uses an idempotency key, records provider acceptance, and retries transient failures with a bounded attempt count. Provider acceptance is not a delivery receipt; vendor callbacks and delivery status reconciliation remain separate provider-specific work.

For production, configure the required Twilio and/or Meta secrets, start with a low traffic test business, verify opt-out and reschedule behavior, and monitor failed outbox rows. If no provider is configured, the worker fails closed and records failed attempts; it never silently falls back to sending through an unrelated channel.

## Legacy-table RLS rollout

Migration `0032_legacy_tenant_row_level_security.sql` enables and forces RLS on every public base table with a `BusinessId` column. The default policy is fail-closed: `app.business_id` must be set and must match the row. `tenantRlsContext.js` carries the authenticated tenant in request-local async context and installs it transaction-locally for pool and checked-out-client queries. The value is sourced from the verified access-token identity, never from a request body or query parameter.

Before production rollout, the database integration suite had to cover all HTTP routes and all background workers; the public, webhook and worker paths now run through lookup policies (`0033`) or per-business loops (`forEachBusiness`), proven in CI. In particular, public storefront/analytics/webhook flows and scheduled workers do not necessarily have a bearer-authenticated request context; each must either establish a validated tenant context after resolving a trusted tenant, or use a separately provisioned narrowly privileged worker connection. Do not solve this by allowing an unset context or by trusting a caller-controlled `app.business_id`. The migration is intentionally fail-closed, so any unconverted access path will receive an RLS denial and should be fixed before deploying the migration to production.

**Staff consent (step-08c).** Staff record consent on the customer page (`GET` and `PUT /api/customers/:customerId/messaging-preferences`). Recording `OptedIn` needs a note of at least 5 characters saying how and when the customer agreed (400 `consent_note_required`); `OptedOut` needs none. Staff records always carry the source `staff_note`; the note and the recording user are kept in `ConsentNote` and `ConsentRecordedByUserId` (migration `0035`). The list marks a row `CustomerOptedOut` when the customer opted out through the link or a standing stop covers the number; staff cannot undo either (409 `customer_opted_out`), and a staff opt-out recorded over a customer's own opt-out keeps the source `customer_link`.

## Editable wording (step-16c)

`NotificationTemplates` (migration `0041`, forced row-level security) holds a business's own wording for a customer message: one row per business, kind (`order.ready`, `order.amended`, `payment.receipt`, `appointment.reminder`) and channel. No row means the default in `src/messaging/templateCatalog.js`, which is the wording sent before step-16c. A template is plain text (at most 600 characters, no links or markup) with only the placeholders of its kind; it is checked when saved and again when used, and a template that cannot be read or is no longer valid is replaced by the default, so a template never stops a message. A template changes words only: who may be messaged, the consent and current-facts checks, and the opt-out line added by the sender are not part of it. Only people with `business.settings` can read or change wording; saves and resets are audited without the text.

## WhatsApp templates and inbound STOP (step-16d)

WhatsApp can start a conversation only through a message template approved by Meta, so the three customer event messages and the appointment reminder are sent as four fixed templates (`src/messaging/whatsappTemplates.js`; names and bodies in `WHATSAPP_SETUP.md`, kept equal to the code by a test). The same facts fill the variables as in the SMS text and the last variable is the personal unsubscribe link. A business's saved wording (step-16c) applies to SMS only; a WhatsApp row saved earlier is ignored when sending, the settings screen shows WhatsApp as fixed, and a save for WhatsApp is refused with 409 `whatsapp_wording_fixed`.

Meta's webhook is `GET` and `POST /api/messaging/whatsapp/webhook`. `GET` answers the one-time verify handshake (constant-time token check). `POST` checks `X-Hub-Signature-256` (HMAC-SHA256 of the exact bytes, app secret) before it reads anything; a bad or missing signature is 403 and records nothing. A STOP (or UNSUBSCRIBE, CANCEL, END, QUIT, STOPALL, also from a tapped button) records a sender-wide stop with source `WhatsAppStop` (migration `0042`) for that WhatsApp address, which blocks every business that holds the number, on WhatsApp only; START lifts only that stop and never restores a consent a customer withdrew. Messages to a number other than ours, delivery statuses and anything malformed are ignored, and at most 100 messages are read per request. A Meta refusal because the person stopped messages (131050) is recorded as a `ProviderRefusal` stop; other Meta errors keep only their numeric code.
